> 用户问题：「等待办的事情」搜不出含「待办事项」的文档；「需要办的事情」也搜不到。
> 全程**真实端到端验证**：所有结论来自正在运行的 MCPHub Desktop（tauri dev，真实 MCP 接口 + 真实索引 13,801 chunks），非模拟数据。

## 一、根因链（逐层实测确认）

| # | 根因 | 证据 |
|---|------|------|
| 1 | **索引 90% 是垃圾**：mermaid.min.js ×2 份 = 12,398 行（90%）| 真实索引 top-2 全是 mermaid（cos 0.713 最高）|
| 2 | **97M 模型各向异性**：中文查询走 byte-fallback = 字节汤向量 ≈ 压缩代码的平均向量 → 垃圾块反而最高分 | granite-97m 实测：中文块之间全部挤在 0.82-0.88 窄带；「Query:」前缀单侧无效 |
| 3 | **向量候选池太小**：fetch=120 行，目标块被窄带噪声挤出候选 | e2e：kwWeight=0 时目标完全缺席 |
| 4 | **关键词通道被关闭**：配置实际 kwWeight=0.0（用户改过）| DB 实查 |
| 5 | **title bonus 的 hits>=2 门槛掐死目标**：目标 title 只含「待办」一个命中词 | TB_DEBUG 日志：`title="消息配置与待办事项..." hits=1` → bonus=0 |
| 6 | **README 霸榜**：19 份 git 仓库同名 README.md（不同目录），title 含「设计」单词 | 长查询 README×5 霸榜 0.8645 |

## 二、落地的修复（全部通过端到端实测）

| 修复 | 内容 | 实测效果 |
|------|------|----------|
| 跨语言惩罚 | 中文查询 × CJK 占比<10% 的 chunk（纯代码=字节汤）平滑降分 45%；混合内容技术文档（ratio≥0.1）不受影响；英文查询查代码零影响 | mermaid 从 #1-2 消失 |
| 向量候选池扩容 | 120 → 500 行 | 目标块进入候选池（前提条件）|
| 独立标题通道 | title bonus 不挂在 kwWeight 上（kw=0 也生效）；质量加权 `precision×coverage×0.5, cap 0.42`（放弃 hits>=2 门槛——门槛版实测把目标掐死）| 「等待办的事情」目标 **#1（0.8452）** |
| 泛化文件名降权 | README/index/package.json 文件名 → bonus 减半 | README 让位，真实架构文档升 #1（长查询）|
| 单文档名额上限 | 每文档最多 5 块 | 防大文档刷屏 |
| 关键词通道窗口 | LIKE 匹配窗口 120 → 4000（无 ORDER BY 的任意子集问题）| kw 通道恢复时生效 |
| 部署模板 | deploy.json：`Query: {query}` / `Title: {title} \| {content}`（占位符模式，{title} 中 `\|`→`_`，全模型通用）| 端到端生效（日志确认 doc_prefix 已加载）|

## 四、剩余缺口（诚实声明）

1. **「需要办的事情」仍搜不到目标**：与「待办事项」**零字面重叠**（需要/要办/办的/的事/事情 vs 待办/办事/事项），title 通道原理上无法覆盖，纯语义又是 97M 模型的窄带天花板。**需要重索引**（Title 模板让每个 chunk 向量携带标题语义）+ 用户换词（如搜「待办」直接命中）。
2. **长查询目标缺席**：目标 title 与「功能的设计」无词元交集（「迭代评审文档」不含「功能/设计」）——重索引后文档侧 Title 模板会把「待办事项」语义注入每个 chunk 向量，预期改善。
3. **README×19 仍占 3-7 名**：它们是 19 个不同目录的真实文档（非重复），向量分本身高。已降权到合理位置。
